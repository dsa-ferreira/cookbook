# cookbook 0.2.0 update

0.2.0 replaces the JSON REST API with an MCP server: clients now call tools at
`POST https://cookbook.lan/mcp`, and open-webui becomes a client. The image
runs one uvicorn process instead of gunicorn, on the same port. The database,
schema, settings and healthcheck don't change.

```yaml
handover_update: 1
service: cookbook
from: 0.1.0
to: 0.2.0

before:
  - >-
    Generate one API key per client with
    `docker run --rm --entrypoint cookbook album.lan/cookbook:0.2.0 apikey claude-code`
    and the same with `openwebui`. Each run prints the plaintext key once and a
    `"<name>": "<hash>"` line.
  - >-
    Add both `"<name>": "<hash>"` lines to the api_keys secret. Keep the existing
    per-user entries for now, so nothing loses access during the switch.
  - Store the openwebui plaintext key as the new openwebui_api_key secret.
  - Remove GUNICORN_CMD_ARGS from the cookbook .env/compose templates if they set it (see Details).

changes:
  - change: changed
    path: service.summary
    value: Recipe store served as an MCP server for AI assistants
  - change: changed
    path: placement.reason
    value: One small uvicorn container plus a Postgres database. Light load (two users, two assistant clients).
  - change: changed
    path: exposure.who_calls_it
    value: [Claude Code on the LAN (MCP over HTTP, bearer key), open-webui (MCP tool server, bearer key)]
  - change: changed
    path: components.api.image
    value: album.lan/cookbook:0.2.0
  - change: changed
    path: components.api.ports[port=8080].purpose
    value: MCP endpoint at /mcp (every path except /healthz needs a bearer key)
  - change: added
    path: secrets.openwebui_api_key
    value:
      generate: user_provided
      used_by: [open-webui]
      rotation: >-
        The plaintext key whose hash is the "openwebui" entry in api_keys
        (from `cookbook apikey openwebui`). Rotate both together; open-webui's
        tool calls get 401 until it has the new key.
  - change: added
    path: integrations.open-webui
    value:
      direction: used_by
      detail: >-
        MCP tool server over Streamable HTTP at https://cookbook.lan/mcp, exactly
        (no trailing slash), with bearer auth using openwebui_api_key.
      tolerates_cold_start: true
  - change: changed
    path: lifecycle.first_run
    value:
      - Create the cookbook database and its owner role in Postgres.
      - Generate one API key per client (claude-code, openwebui), put the hashes in the api_keys secret and the openwebui plaintext key in openwebui_api_key.

      - Register cookbook as an MCP tool server in open-webui with openwebui_api_key.
  - change: changed
    path: verify
    value:
      - "curl -s https://cookbook.lan/healthz  →  {\"status\":\"ok\"}"
      - "curl -s -o /dev/null -w '%{http_code}' -X POST https://cookbook.lan/mcp  →  401"
      - >-
        curl -s https://cookbook.lan/mcp -H 'Authorization: Bearer <key>'
        -H 'Content-Type: application/json' -H 'Accept: application/json, text/event-stream'
        -d '{"jsonrpc":"2.0","id":1,"method":"tools/call","params":{"name":"list_units","arguments":{}}}'

        (g, kg, ml, l, tsp, tbsp, cup, piece, clove, can, pinch); this proves auth, MCP, DB access and migrations

after:
  - Register cookbook in open-webui as an MCP (Streamable HTTP) tool server, URL https://cookbook.lan/mcp, bearer auth with openwebui_api_key.
  - Give the claude-code plaintext key to the user, who registers the server in Claude Code (see clients).
  - Once both clients work, remove the old per-user entries from api_keys and restart api.

verify:
  - "curl -s -o /dev/null -w '%{http_code}' -H 'Authorization: Bearer <key>' https://cookbook.lan/units  →  404 (the REST API is gone)"
  - In open-webui, a chat with the cookbook tools enabled can call search_ingredients.

clients: >-
  Callers of the REST API break: /units, /ingredients and /recipes now return
  404. Claude Code registers the server with
  `claude mcp add --transport http cookbook https://cookbook.lan/mcp --header "Authorization: Bearer <key>"`
  (the machine must trust the homelab CA). open-webui is configured by the
  infra side (see after).
rollback: >-
  Pin album.lan/cookbook:0.1.0 again. Its image sets GUNICORN_CMD_ARGS itself,
  and the schema is unchanged, so no restore is needed. The per-user keys work
  again as long as their api_keys entries are still there.
```

## Details

- **Server process.** gunicorn (2 workers, configured by `GUNICORN_CMD_ARGS`)
  is replaced by a single uvicorn process. The image CMD is
  `uvicorn --factory cookbook.app:create_app --host 0.0.0.0 --port 8080 --proxy-headers`.
  `GUNICORN_CMD_ARGS` is no longer read. The handover only described it as a
  default baked into the image, so the infra side may never have set it, but
  if a template does, remove it. The resource TODOs from the handover still
  apply, now to one process.
- **Proxy.** Forward `/mcp` exactly. `/mcp/` answers with a 307 redirect, and
  some MCP clients drop the `Authorization` header when they follow one.
  Responses are plain JSON, not event streams, so the proxy defaults (1m body,
  60s) are still enough.
- **`FORWARDED_ALLOW_IPS`** (new, optional, read by uvicorn). With
  `--proxy-headers`, uvicorn trusts `X-Forwarded-*` only from 127.0.0.1 by
  default. Set it to the reverse proxy's IP to see real client IPs in
  uvicorn's request log. It is safe to leave unset.
- **Host header.** The MCP SDK's DNS-rebinding check is turned off in code, so
  requests with `Host: cookbook.lan` are accepted. The bearer key remains the
  access control.
- **Keys per client.** The `api_keys` format is unchanged. Its entries are now
  one per client (`claude-code`, `openwebui`) rather than one per user, so the
  access log tells the clients apart and either can be revoked alone.
- **Access log.** Lines now include the tool name for tool calls, e.g.
  `POST /mcp 200 key=openwebui tool=delete_recipe`. They still never contain
  the key.
- **No downtime steps.** There are no migrations; the switch is a normal
  container restart.
